# 03. 프론트엔드 구현 지침

## 1. 책임 범위

프론트엔드는 입력을 받고, 사용자에게 상태를 보여주며, 백엔드 API에
요청한다. OpenAI 또는 Supabase에 직접 연결하지 않는다.

## 2. HTML 구조

`index.html`은 시맨틱 구조를 사용한다. - `header`: 브랜드와 내비게이션 -
`main`: 히어로와 감성 분석 - `section`: 입력 폼 - `section`: 분석 결과 -
`footer`: 간단한 서비스 안내

textarea에는 `id`, `name`, `maxlength="2000"`, `required`를 설정한다.
글자 수는 JavaScript로 갱신하되 서버 검증도 유지한다.

## 3. 프론트엔드 모듈 역할

-   `js/app.js`: 앱 초기화, 이벤트 연결, 상태 흐름 제어
-   `js/api.js`: `/api/analyze` 요청 및 응답 처리
-   `js/ui.js`: 로딩/결과/오류 렌더링
-   `js/validators.js`: 공백, 글자 수 등 입력 검증

전역 변수와 하나의 거대한 스크립트에 모든 로직을 넣지 않는다.

## 4. 상태 모델

화면 상태는 다음 중 하나로 관리한다. - `idle`: 아직 분석하지 않음 -
`loading`: 분석 요청 중 - `success`: 정상 결과 수신 - `error`: 오류 발생

상태 전환 규칙: 1. 최초에는 `idle`. 2. 유효 입력으로 요청을 시작하면
기존 결과/오류를 초기화하고 `loading`. 3. 정상 응답 및 스키마 검증 성공
시 `success`. 4. API 오류, 네트워크 오류, 응답 검증 실패 시 `error`. 5.
사용자가 입력을 수정하면 이전 결과가 현재 입력의 결과로 오인되지 않게
결과 표시를 지우거나 "이전 분석 결과"로 혼동되지 않게 처리한다.

## 5. 요청 계약

-   메서드: `POST`
-   경로: `/api/analyze`
-   요청 헤더: `Content-Type: application/json`
-   요청 본문:

``` json
{
  "text": "오늘은 좋은 일이 많아서 기분이 좋다."
}
```

-   성공 응답의 구조는 `docs/04-backend-api.md`를 따른다.

프론트엔드는 HTTP 상태 코드와 응답의 `error.code`를 함께 확인한다. 응답
JSON 파싱 실패도 오류로 처리한다.

## 6. 사용자 경험 규칙

-   공백 입력이면 요청하지 않고 `문장을 입력해 주세요.` 표시
-   2,000자 초과면 요청하지 않고 길이 안내
-   요청 중 버튼 비활성화 및 로딩 문구 표시
-   Enter는 textarea에서 줄바꿈으로 동작한다. 제출은 버튼 클릭 또는
    명시적인 폼 제출 동작으로 수행한다.
-   결과 라벨은 한글로 매핑한다.
-   신뢰도는 정수 `%`로 표시하되 "참고용"임을 함께 표기한다.
-   분석 이유는 텍스트 노드로 안전하게 렌더링한다.
-   재요청이 시작되면 이전 요청의 결과가 뒤늦게 덮어쓰지 않도록 요청
    식별자 또는 `AbortController`를 활용한다.

## 7. 보안 및 안전한 렌더링

-   사용자 입력과 AI 응답을 `innerHTML` 문자열로 삽입하지 않는다.
-   `textContent`와 DOM 요소 생성으로 출력한다.
-   API 키, 모델명, 서버 내부 오류 상세를 클라이언트에 전달하지 않는다.
-   서버에서 반환한 오류 메시지도 허용된 사용자용 메시지만 표시한다.
-   프론트엔드에서 임의로 신뢰도나 감성 라벨을 생성하지 않는다.

## 8. 완료 기준

-   입력, 글자 수, 검증, 로딩, 성공, 오류, 재분석 흐름이 동작한다.
-   모바일 및 데스크톱에서 입력이 편리하다.
-   요청 중 중복 클릭을 막는다.
-   AI 결과가 아닌 임의의 더미 결과가 실제 서비스 흐름에 남아 있지 않다.
    개발용 mock은 테스트 환경에서만 사용한다.
